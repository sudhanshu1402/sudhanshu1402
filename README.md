## keel

Write work as named steps. When a step finishes its result is journaled, so a process that dies at step 7 resumes at step 7 instead of starting over. Same idea as Temporal or Vercel Workflow, without the server, the database or the build step. Zero runtime dependencies.

<div align="center">
<img src="https://raw.githubusercontent.com/sudhanshu1402/keel/main/demo/demo.gif" alt="keel: run 1 charges a card and crashes, run 2 resumes and ships without re-charging" width="720" />
</div>

Run 1 charges a card and dies before shipping. Run 2 resumes and ships, and the card is charged once. Reordering or renaming steps between runs trips a divergence guard. It's a positional check, so it catches renames and reorders, not a rewritten step body at the same name and position.

<div align="center">
<picture>

That last number is the honest one, and note the gap is three decades wide, not a couple of steps. `FileStore` rewrites and fsyncs the whole file on every commit, so the 5,000th step costs far more than the first. It's the default because it needs nothing installed, not because it's fast. [Benchmark notes](https://github.com/sudhanshu1402/keel/blob/main/docs/BENCHMARKS.md).

<summary><h2>How the repos fit together</h2></summary>

Every box below except `request` is a separate repo. They aren't one deployed platform. Each takes a single segment of an ordinary request path and isolates the way that segment fails.

```mermaid
graph LR
    REQ([request]) --> AUTH["auth<br/>SAML, SCIM, per-tenant secrets"]
    AUTH --> Q["queue<br/>priority, backoff, workers"]
    Q --> WORK["work<br/>durable steps, resume after crash"]
    WORK --> DB[("data<br/>region-pinned shards")]
    WORK --> LLM["llm<br/>schema-checked output, provider failover"]
    AUTH -.-> OTEL[["traces and metrics"]]
    Q -.-> OTEL
    WORK -.-> OTEL
```

Reference implementations, not production deployments. Each README says what it is and what it isn't. The failure mode in the second column is what each one is actually for.

| Repo | The problem it exists to handle |
| :-- | :-- |
| **[enterprise-auth-stack](https://github.com/sudhanshu1402/enterprise-auth-stack)**<br/><sub>[write-up](https://sudhanshu1402.github.io/system-design-portal/auth-stack/)</sub> | A cached SAML strategy keeps failing after a certificate rotation until something evicts it. Rebuilding per request costs a Secrets Manager call and makes rotation take effect immediately. |
| **[distributed-queue-engine](https://github.com/sudhanshu1402/distributed-queue-engine)**<br/><sub>[write-up](https://sudhanshu1402.github.io/system-design-portal/queue-engine/)</sub> | The queue key is `{emails}:outbound`. That hash tag pins every key for the queue to one Redis Cluster slot, which is what BullMQ's multi-key Lua scripts need if you ever move off a single node. |
| **[multi-region-mongo-patterns](https://github.com/sudhanshu1402/multi-region-mongo-patterns)**<br/><sub>[write-up](https://sudhanshu1402.github.io/system-design-portal/mongo-sharding/)</sub> | `POST /users` returns 409 when a user's region doesn't match its tenant's zone. A record physically can't land in a zone that violates its tenant's residency. |
| **[otel-sdk-node](https://github.com/sudhanshu1402/otel-sdk-node)**<br/><sub>[write-up](https://sudhanshu1402.github.io/system-design-portal/tracing-sdk/)</sub> | Auto-instrumentation patches modules on `require`, so anything imported before `sdk.start()` is never patched and its spans silently vanish. That's the bug people lose an afternoon to. |
| **[llm-assessment-pipeline](https://github.com/sudhanshu1402/llm-assessment-pipeline)**<br/><sub>[write-up](https://sudhanshu1402.github.io/system-design-portal/llm-pipeline/)</sub> | The model will occasionally emit zero correct options, or three. A Zod refinement enforces exactly one, and a violation is rejected before anything is stored. |

<details>
<summary><h2>How I work</h2></summary>

<br />

- I reach for the boring, well-understood tool first. Novelty is a cost you pay at 3am.
- I like problems that only show up under failure: retries, partial writes, a process that dies mid-transaction. That's usually where the real design is.
- I write the runbook and the traces before I call something done. If I can't see what a system is doing, I don't trust it.
- A background in data means I care where numbers come from. One correct metric beats five plausible ones.

</details>
